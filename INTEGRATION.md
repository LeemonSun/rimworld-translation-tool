# Sol Translation Tool 2.1 — вход для Сола

Рабочая папка: `D:\LeemonProekt\RimWorldTranslationTool`. Использовать **sol.py / SOL.cmd**, старый tool.py — совместимый внутренний слой, а не основной интерфейс. Новые зависимости и API не нужны для технического цикла. Первичная диагностика: `python sol.py doctor`.

## Обычный цикл

```powershell
Set-Location D:\LeemonProekt\RimWorldTranslationTool
python sol.py open 'D:\папка-мода-или.zip' --version 1.6 --language en --mods brrainz.harmony
```

Программа сама определяет оригинальный packageId, создаёт/возобновляет папку `runs/...` и возвращает её как `job`. В `--mods` перечислить реально проверяемые дополнительные DLC/моды по packageId. Не заявлять непроверенные версии. Для китайских источников `--language zh-Hans`. ZIP должен содержать один оригинальный мод.

Дальше читать **STATUS.json и requests.json**, затем только перечисленные там активные requests/*.json. Не загружать весь job.json, assemblies.json, базу или старую переписку. В каждой партии отдельно `translations` (новые строки/контекст/подсказки) и `source_review` (реальные технические вопросы). Память/технические решения повторно не спрашиваются, если применимый контекст не изменился.

Ответ — JSON:

```json
{
  "request_id": "полный ID из партии",
  "translations": {"полный ID строки": "Русский перевод"},
  "source_review": [
    {"id": "ID вопроса", "decision": "technical", "reason": "Конкретное объяснение, почему это не отображаемый текст"}
  ]
}
```

Набор ID переводов обязан точно совпасть с ЭТОЙ партией. Нельзя перемешивать партии/старые ID. Для партии только с вопросами translations = {}. Технические решения можно дать частично. Импорт:

```powershell
python sol.py answer 'ПАПКА_JOB' response.json
python sol.py review 'ПАПКА_JOB' --reason 'Исходный контекст и смысл переводов проверены; внесены редакторские правки'
```

`answer` сохраняет receipt и черновик. Только `review` принимает в память. Новые поля/патчи могут породить следующий короткий пакет — смотреть STATUS.json. `python sol.py request JOB` пересобирает текущие партии. `review` сам это делает. Если надо исправить черновик до принятия, импортировать исправленный ответ той же актуальной партии. После принятия поправку удобно внести через старый локальный редактор либо `tool.py import` с текущей строкой и `tool.py accept`; затем `sol.py request`.

Когда next=finish:

```powershell
python sol.py finish 'ПАПКА_JOB' --package leemonsun.mod.russian
python sol.py verify 'ПАПКА_JOB'
```

`verify` проверяет память, актуальность оригинала и хеши, при необходимости запускает игру скрыто в НОВОМ отдельном профиле. Возможно потребуется разрешение среды на создание изолированных ссылок/запуск игры. Пользовательский профиль не используется. Зависимости дополнительно: `--dependencies 'D:\папка-зависимости'`. Игровая проверка поддерживает XML Keyed и DefInjected, списки, установку автоматически созданного Harmony-патча и его русский/английский guard. Strings требуют отдельного runtime-адаптера — программа не ставит им ложный PASS.

Результат: **DELIVERY.json**, отдельная папка перевода и ZIP. `ready_for_existing_release_workflow=true` означает: технические проверки, явное принятие, фактические значения в игре и классификация языкового отчёта пройдены. Это не доказательство литературного качества или всех игровых механик. Обложка, Steam ID и публикация остаются прежним проверенным процессом. Ничего автоматически в Steam не отправляется.

## Технические решения

- `technical`: строка/источник не требует перевода; дать конкретное основание.
- `covered`: источник уже покрыт существующими ключами/контекстным каталогом; указать подтверждение, а не предположение.
- `translate`: для `custom-field` автоматически добавить найденное нестандартное поле в следующую партию. Не нужно вручную собирать каталог.
- `needs_patch`: только для проверенного метода; `patches: [{"ordinal":0,"source":"точный IL-литерал"}]`. Программа создаёт Keyed, затем компилирует отдельный языковой патч, ограниченный SHA256 оригинальной DLL, методом и порядковым номером литерала. Никакой массовой замены ldstr. Не применять к сохранённым ID, сериализации или составным фрагментам без анализа.
- `artifact`: сложный случай требует ранее проверенной минимальной языковой DLL; `artifact: "D:\\...\\LanguagePatch.dll"`. Только отдельная языковая DLL, не DLL оригинала. Она фиксируется по SHA256 в state/artifacts, добавляется Harmony и остаётся частью последующих повторных запусков. Её конкретные методы/отладочные атрибуты проверять специальным стендом дополнительно к общему value-check.
- `unresolved`: источник ещё не разобран, выпуск блокируется.

Любое решение может включать `rows: [{type,key,text,role,context}]` — дополнительные проверенные записи для новых партий. Сохранённое решение привязано к содержимому вопроса и контексту. Сломанный XML, ошибки разбора DLL и коллизии не разрешается снять словесным решением.

В `format_reviews: {"ID":"обоснование"}` можно явно подтвердить намеренное грамматическое изменение формата. Причина привязывается к точной паре исходник/перевод. Не использовать для маскировки потерянного аргумента. Вопросы не следует поголовно отмечать covered ради зелёного статуса.

## Экономия, API и обслуживание

Смысл/новые тексты переводит Сол либо необязательный настроенный API. Без памяти неизвестный текст не появляется из ничего. Технические операции не вызывают модель.

API-режим: `python sol.py api-prepare JOB` → передать созданный api_manifest.json существующему `RimWorldTranslations/tools/api_batch.py` с явным бюджетом → `python sol.py api-import JOB '.../all_drafts.json'`. Клиент сохраняет свои receipts; повторно платный запрос при наличии receipt не выполнять. Никакие ключи в чат/базу/отчёт не копировать. Ответ API остаётся draft, технические вопросы и смысловая приёмка остаются Солу.

Память: `state/memory.sqlite3`; `python sol.py backup` создаёт SQLite backup. Внешние скопированные языковые патчи и metadata-кэш — соседние подпапки state. Не удалять state/artifacts отдельно от базы. `tool.py revoke ID --reason ...` отзывает перевод и показывает затронутые применения; `sol.py audit-revoke TASK_ID --reason ...` отзывает техническое решение. Старые публикации не меняются. История переводов и технических решений хранится в базе. `tool.py rollback SEQ --reason ...` — откат исправления перевода. При восстановлении полного состояния закрыть инструмент и вернуть согласованную копию базы + artifacts.

Обновление мода: снова `open` оригинала — новый снимок автоматически; без изменений возобновляется старый job. Если оригинал изменился после открытия, verify блокируется до нового open. Не менять snapshot/job.json вручную. API, токены и секреты в продуктовый ZIP не включены.

## Подтверждено на этом ПК

13 автоматических тестов, цикл через Tk-виджеты, три новых изолированных игровых прогона: LayeredApparel 520 Keyed; FactionWeaponsApparel 16 Keyed + сгенерированный scoped-патч; SimpleLeadership 138 Keyed + 114 Def-полей и существующий проверенный языковой адаптер. Повторное открытие: 0 строк/0 технических вопросов, 0,1–0,6 с. Полные сведения — PRODUCT_REPORT.md, PRODUCT_METRICS.json и product-tests/*-final/GAME_TEST.json.

Игра в выполненных прогонах сообщает Version.txt **1.6.4633 rev1260**; старые отчёты с rev1261 не подменяют этот результат. Языковой отчёт содержит предупреждения официальной локализации: отдельно запущенная Core+Harmony с пустыми тестовыми модами дала ТОЧНО такой же отчёт; классификация привязана к SHA256 отчёта и Assembly-CSharp. При другом отчёте verify требует разбор и `--report-reason 'конкретная классификация'`, не скрывает ошибки.

Поддержка сложных новых схем расширяется через явные source_review, доп. записи и отдельные языковые адаптеры. Любую произвольную DLL/механику без контекста программа не объявляет полностью переведённой. Именно блокирующие неизвестные случаи позволяют доверять техническому результату в заявленном объёме.
